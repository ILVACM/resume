## 适用领域分组

互联网

## 方案构建意图简述

① 本组为有核心自有产品业务的公司集团（纯 AI 公司归「agent」）；最看重完整项目从立项到上线的交付能力与算法底子。
② 本方案选「机场物流（总负责人，撑全生命周期交付与统筹）+ 光点短视频（撑微服务解耦与推理调度）+ 测绘院知识库（撑 PB 级数据处理与权限治理）+ 算法竞赛（撑算法硬实力）」四条为骨架。
③ 与同届相比，形成"能独立扛交付 + 有规模化数据处理 + 算法有硬背书"的组合，而非只写过业务代码。

## 关键优势项目
- 关键项目1：
    需要突出的要点有：`90 万合同项目总负责人 + 全生命周期交付；系统架构演进（Hub-Spoke 通信中枢）与架构治理（二维数据分类 / 边缘设备五态机）——大厂看工程成熟度、责任与协作；分支：业务后端/客户端岗看交付与统筹，基础架构岗看架构演进与云边监控体系`  
    示范内容如下：
```markdown
#### 机场物流集团 | 智慧物流系统迭代二期 项目总负责人 | 2025.07 - 2026.09
**相关技术栈**：Spring Boot / Docker / MySQL / Redis / Prometheus / Grafana / 边缘推理（32 TOPS INT8）

**项目背景**：机场转运库区依赖人工巡逻与事后录像回溯，违规行为发现滞后、取证难，无法满足多库区规模化实时监管需求。
**项目定位**：校企联合框架二期（合同 55 万 / 累计框架 90 万），本人任二期总负责人独立统筹全生命周期。

**核心工作**：
- 针对库区多场景违规识别需求，主导设计「边缘轻量推理 + 中央归档检索」多端协同分层架构，落地车辆超速、人员离岗、晕倒摔倒等 11 类违规的 AI 视觉算法
- 针对组件间两两耦合导致扩展困难的问题，主导平台架构由 Spring Boot 分层 → 纵向分层 → 星形 Hub-Spoke 拓扑演进，使新增业务组件仅需对接中枢单一契约
- 针对项目无运维保障体系的现状，搭建 Docker 容器化 B/S 部署与 Prometheus+Grafana 云边监控体系（15+ 告警），将 P1 故障恢复时间压缩至 5 分钟内、系统可用性提升至 99.5%

**成果**：按期高质量验收交付，甲方委托横向拓展二期。
```
- 关键项目2：
    需要突出的要点有：`微服务解耦 + 异步任务编排 + 混合推理调度——互联网工程风格的标准化设计；分支：后端/平台岗看服务化与队列设计，AI 应用岗看推理调度`  
    示范内容如下：
```markdown
#### 广州光点信息科技股份有限公司 | Python 开发实习生（AI 研发组） | 2025.03 - 2025.06
**相关技术栈**：Python / FastAPI / vLLM（Qwen2.5-14B、Llama 3） / Celery / Redis / 大模型 API

**项目背景**：企业全媒体热点运营依赖人工完成"监控-脚本-数媒合成"全链路，单条热点到视频产出需数小时，运营效率低。
**项目定位**：AI 研发组实习，负责微服务化架构与推理调度模块。

**核心工作**：
- 针对大模型能力与业务逻辑耦合导致的迭代效率低下问题，基于 FastAPI 将「要点提取/脚本二创」能力拆为独立微服务（标准化 REST 接口），使业务迭代与模型升级互不阻塞
- 针对全量调用云端 API 成本高、全量本地推理质量受限的三角困境，设计本地 vLLM（Qwen2.5-14B / Llama 3）处理常规任务 + 复杂创意路由云端 API 的混合调度策略
- 针对下游数字人系统跨团队交接的数据一致性问题，引入 Celery + Redis 异步队列并以标准化 JSON 协议对接脚本/时间轴/素材元数据，实现跨系统自动化流转

**成果**：单条热点到视频产出从人工数小时压缩至 15 分钟内。
```
- 关键项目3：
    需要突出的要点有：`PB 级数据 + 微内核六层架构（检索环节可独立替换）+ 千万级向量存储——大规模数据处理与系统架构设计能力；分支：数据/存储方向看流水线与向量库，算法方向看检索增强，架构岗看微内核与可替换性设计`  
    示范内容如下：
```markdown
#### 广东省国土资源测绘院 | 系统开发实习生（卫星应用中心） | 2025.07 - 2025.10
**相关技术栈**：Python / FastAPI / Milvus / vLLM（Qwen3） / BERT / Docker / Nginx / LangChain / RAG

**项目背景**：测绘院 PB 级非结构化专业文档与地理空间数据长期分散存储，依赖人工检索且受"数据不出域"合规约束，效率低下。
**项目定位**：实习项目，主导 RAG 系统核心架构与本地化部署全链路交付。

**核心工作**：
- 针对数据分散且不能出域的合规约束，设计「逻辑核心 + 功能插件」微内核 + 六层分层架构，使检索链路各环节可独立替换而不触动核心，满足模块化迭代要求
- 针对内部/外部查询的数据隔离需求，基于 BERT 微调实现意图二分类路由（内部走本地库、外部经安全通道受控访问），配套三级权限治理，确保数据不出内网
- 针对项目初期甲方对大模型期望过高的问题，通过多轮需求调研与早期 Demo 量化评估数据管理期望，将项目目标从「开放式通用问答」收敛至「精准检索与故障排查」，规避范围蔓延

**成果**：专业问答忠实度≥95% / 相关率≥90%，交付需求/技术方案/测试/工作总结完整文档链。
```
- 关键项目4：
    需要突出的要点有：`Agent 规约体系构想设计——工程规范与可追溯治理能力；分支：大厂看工程治理体系与 Git 追踪机制，平台 / 基础架构岗看规约与契约意识`  
    示范内容如下：
```markdown
#### Agent 规约体系构想设计 | 个人思考实践 | 2026.08 - 至今
**相关技术栈**：多 Agent 协作 / 规约工程 / AGENTS.md / Git / CI

**项目背景**：直接向 agent 下达任务存在产出不可靠、依赖无歧义引导的问题，需要一套工程规约使「人主导设计验收、规约约束 agent 交付」。
**项目定位**：个人独立立项的方法论探索，把「提示词工程」升级为可验证的规约体系。

**核心工作**：
- 针对多 Agent 协作中上下文易丢失、任务易偏移的问题，设计约束层 / 知识层 / 实例层三层逻辑 + AGENTS.md 与 .spec/ 双载体，使 Agent 仅凭体系内文件即可重建上下文
- 针对 Agent 任务执行过程不可追溯的痛点，设计任务锚点三层追踪机制（锚点只存 5 秒摘要），辅以 Git 提交双向绑定定位每次任务执行现场
- 针对规约体系落地可能过度工程化的风险，主动保留「无脚本降级模式」，用户可随时跳过规约自由操作，使体系具备可用性与工程弹性的平衡

**成果**：产出 4 份设计文档，已在个人仓库落地运行。
```
