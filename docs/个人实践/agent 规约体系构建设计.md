## 1. 目标总述

### 1.1 交付物定义

> 来源：体系定位（构建指令总目标）

- 构建指令的最终交付物，是使目标项目仓库具备一套**完全符合要求的 agent 规约体系**
- 构建指令的全部要求执行完毕后，该仓库即处于「**规约体系已建立且自洽**」的终态
- 该体系服务于后续所有工作会话：任何 Agent 进入仓库后，仅凭体系内文件即可重建上下文并正确行动

### 1.2 适用环境

> 来源：体系定位（构建指令总目标）

- **目标仓库**：本地 Agent 的运行目录，即 Agent 工具（如 TRAE、Workbuddy）所打开的项目仓库
- **执行主体**：具备文件读写、目录遍历、代码搜索与多 Agent 协作能力的本地 Agent
- **体系读者**：后续进入该仓库的任意 Agent（主要读者）与人类开发者（次要读者，经 `README.md` 与 `AGENTS.md`）

### 1.3 终态判据

> 来源：§1

规约体系建立完成后，须同时满足以下九条标准：

1. Agent 仅凭读取 `AGENTS.md` 即可理解项目全貌并正确路由到所需文档
2. 三层之间职责清晰、无重叠、无遗漏
3. 文档间链接可达、无死链、无孤立文档
4. 约束力层级明确，冲突处理规则完备
5. 实例层实际文档位于项目业务自然位置，不设立 `knowledge/`、`instances/` 等用于集中收纳实例文档的独立顶层目录（规约体系载体 `.spec/` 不在此限）
6. 元信息区完整且格式统一
7. 维护规则可操作、可追溯
8. 任务执行锚点记录追踪机制已嵌入 `AGENTS.md`，详情层目录 `.spec/task-records/` 已建立
9. Git 提交追踪机制已嵌入 `AGENTS.md`，锚点层含 `关联提交` 字段，提交消息格式与回滚红线已明确规定（见 4.8）

## 2. agent 规约体系逻辑结构组成

### 2.1 三层逻辑划分

> 来源：§3、§4

agent 规约体系在**逻辑上**分为三层，三层职责分离、无重叠、无遗漏：

- **约束层**——全体 Agent 必须遵守的硬性规则，是体系的「最高宪法」
  - 内容：项目上下文、核心规则、全局约束、层级治理、锚点机制规定、子目录职责边界
  - 特征：简洁、稳定、高频读取、低频修改
  - 禁止包含：具体实现细节、领域知识、实例文档内容
- **知识层**——项目级通用知识
  - 内容：编码规范、架构设计、API 契约、安全策略、测试策略、部署流程、领域知识
  - 禁止包含：具体模块的实现细节（属实例层）
- **实例层**——具体功能模块/服务/组件的实现细节
  - 内容：模块说明、配置详解、接口实现、故障排查手册、变更日志
  - 禁止包含：跨领域通用规则（属知识层或约束层）

> 三层为逻辑划分，其**实际存放路径**见第 3 章。逻辑分层与实际文件结构是两件事，不可混为一谈。

### 2.2 约束力层级

> 来源：§14

- 冲突时的优先级：**约束层 > 知识层 > 实例层**
- 低层级文档不得违反高层级规则
- 高层级规则不适用于特定场景时，须通过正式豁免流程处理（见 2.6、5.3）

### 2.3 继承与扩展规则

> 来源：§6

- **约束层 → 知识层**：知识层文档必须遵守约束层规则，可在不违反前提下细化
- **约束层 → 实例层**：实例层文档必须遵守约束层规则，不可覆写
- **知识层 → 实例层**：实例层可引用知识层文档作为依据，可补充但不可矛盾
- **实例层 → 知识层**：禁止反向依赖；若发现通用模式，应提炼至知识层
- **同级文档**：允许交叉引用，但须避免循环依赖

### 2.4 管辖范围边界

> 来源：§7

为防止职责模糊，以下场景归属必须明确：

| 场景 | 归属 | 理由 |
|------|------|------|
| 「所有 API 必须使用 RESTful 风格」 | 约束层 | 全局强制规则 |
| 「RESTful API 设计最佳实践」 | 知识层 | 通用知识，非强制 |
| 「用户认证 API 的具体实现」 | 实例层 | 具体模块细节 |
| 「Git 提交消息格式」 | 约束层 | 全局强制 |
| 「Conventional Commits 规范详解」 | 知识层 | 通用知识 |
| 「auth-service 的提交历史分析」 | 实例层 | 具体模块上下文 |
| `.spec/task-records/` 中的任务记录 | 独立于三层体系 | 由 `AGENTS.md` 锚点机制直接管辖，不属于知识层 |

### 2.5 冲突处理规则

> 来源：§14

- 发现层级冲突时，以高层级为准（优先级见 2.2）
- 冲突必须记录，记录写入 `.spec/task-records/` 当前任务详情层**长期留存**
- 冲突记录属于治理证据，**不得**写入临时目录 `_temp/`

### 2.6 豁免规则

> 来源：新增机制（补充 §14 中「正式豁免流程」的实质内容）

**设计目的**

- 在极少数极端情况下，低层级文档因实际业务约束无法完全遵守高层级规则时，允许在**显式记录说明冲突情况**后进行豁免
- 该机制是对严格约束力的补充，**不是削弱**；用于解决少数极端情况，而非常规绕行路径

**触发条件（须同时满足三项）**

1. 实际业务需求无法通过其他方式满足，且该需求与高层级规则存在直接冲突
2. 冲突范围仅限于特定场景或特定文档，不得扩展为通用规则
3. 冲突条款明确可描述，能精确指出违反了哪条高层级规则（精确到条款、章节）

**禁止豁免的情形**

- 全局安全红线（权限控制、数据加密等）
- 三层体系架构本身（约束层 > 知识层 > 实例层 的层级关系）
- 禁止反向依赖规则（实例层不得反向引用知识层）
- 以「方便开发」或「提高效率」为理由的豁免

**管控原则**

- **例外性**：豁免是特例不是常规路径，每次须证明不存在替代方案
- **显式性**：所有豁免必须在文档中明文声明，不得隐性违反高层级规则
- **可追溯性**：每条豁免均有独立记录，可随时审计
- **最小化**：豁免范围严格限定于冲突条款本身，不得借机扩大偏离
- **定期审视**：Tech Lead / 架构师应定期审查已批准豁免，确认是否仍合理

> 豁免的执行步骤见 5.3。

## 3. agent 规约体系实际文件结构组成

### 3.1 载体分布

> 来源：§3、§4、§5

实际文件结构收敛为**两处载体**：

- **① 仓库根目录 `AGENTS.md`**
  - 整个 agent 规约体系的**总入口**
  - 同时是**约束层的唯一载体**（「最高宪法」）
  - 其章节结构即约束层的索引（见 3.3）
- **② 仓库根目录 `.spec/`**
  - 除实例层实际文档外，**其余全部规约体系内容**均存放于此
  - 包含：知识层文档（可按领域建子目录，如 `.spec/architecture/xxx.md`）、实例层索引条目（登记于 `.spec/INDEX.md`）、任务记录目录（`.spec/task-records/`）
  - `.spec/task-records/` 属锚点机制详情层，**非知识层内容**（见 2.4）
  - **命名与隐藏属性意图**：`.spec` 取自 specification（规约），点前缀使其成为隐藏目录——既表明「这是规约」，更以隐藏属性强调「**这是系统级底层规则，请勿随意触碰**」，降低人类与 Agent 误改概率
  - **版本控制要求**：`.spec/` 是规约体系的正式内容载体，**必须纳入版本控制**，严禁加入 `.gitignore`（与 `_temp/` 要求相反，见 4.6）
  - **豁免立场**：`.spec/` 内文件**不享有**任何临时目录豁免——须含 YAML 元信息区、须登记 INDEX、须接受全局校验、修改须触发锚点机制

**实例层区分规则（关键，必须严格区分）**

- 实例层的**索引条目**属于规约体系内容 → **必须**在 `.spec/INDEX.md` 中登记
- 实例层的**实际文档**不属于 `.spec/` 内容 → 保留在项目业务自然位置（如 `src/auth-service/README.md`）

### 3.2 目录结构约束

> 来源：§1、§4

**正向要求**

- 实例层实际文档必须位于项目业务自然位置，不做集中存放
- `.spec/` 下允许按领域建立知识层子目录（如 `.spec/architecture/`、`.spec/coding/`）
- **项目自有 `docs/` 目录的处理**：目标项目若已存在自有 `docs/`（或其他既有文档目录），其内容经构建时判定属知识层的，**文档实体留在原处不迁移**，但**必须**在 `.spec/INDEX.md` 的「知识层文档索引」区块登记（沿用实例层「索引在内、实体在外」模式）
- **新增知识层文档的落位**：构建后新增的知识层文档一律写入 `.spec/`（可建领域子目录），不写入项目自有 `docs/`

**禁止清单**

- 禁止设立 `instances/`、`knowledge/` 等独立顶层目录用于集中收纳实例文档
- 禁止在 `.spec/` 下设立实例文档子目录
- 禁止将 `.spec/` 加入 `.gitignore`
- 禁止把规约体系内容（约束层规则、索引文件、任务记录）写入项目自有 `docs/`；该目录仅承载项目原有文档
- 所有实例层实际文档统一通过 `.spec/INDEX.md` 的「实例层文档索引」区块登记导航

### 3.3 索引与路由

> 来源：§5.1~5.3

索引职责按三层分工，**不设冗余索引文件**：

- **① 约束层索引**——由 `AGENTS.md` **自身的章节结构**承担
  - 3.4 规定的九类章节即约束层的索引单元
  - 约束层**不设外部索引文件**；`AGENTS.md` 本身即体系根入口，Agent 读取该文件即完成约束层全量导航
  - 因章节集合已由 3.4 固化，**不另设显式章节目录（TOC）小节**，避免目录与正文漂移
- **② 知识层与实例层索引**——由 `.spec/INDEX.md` 承担
  - 它是 `.spec/` 内容的**唯一索引入口**
  - 内部划分两个区块：
    - 「知识层文档索引」：指向 `.spec/` 下各知识文档（含领域子目录内文档），**以及留存在项目自有 `docs/` 等原处的既有知识层文档**（见 3.2）
    - 「实例层文档索引」：指向项目各处实例层实际文档，含仓库根目录的 `README.md`
  - 本地 Agent 进入 `.spec/` 后，统一由 `.spec/INDEX.md` 指引跳转
- **③ 向上回链**——`.spec/INDEX.md` 顶部设一行「体系总入口」回链指向 `AGENTS.md`
  - 作用：使经搜索或子目录直接进入 `.spec/` 内部的 Agent 可返回约束层
  - 该回链**仅为指针**，不携带任何约束层内容（见 6.3）

**路由方向**

- `AGENTS.md` 的「文档路由」章节**唯一指向** `.spec/INDEX.md`，不再指向其他索引文件

> 链接书写规范见 6.2；防重复要求见 6.3；隐藏目录的可发现性要求见 6.5。

### 3.4 AGENTS.md 必含章节

> 来源：§5.1

`AGENTS.md` 必须包含以下九类章节（**顺序可调，但必须完整**）：

1. **项目上下文**——技术栈、业务域、团队规模
2. **核心规则**——命名约定、分支策略、提交规范、审查要求（提交规范须含消息格式模板与任务锚点 ID 携带要求，见 4.8.2）
3. **执行模式判定**——单 Agent / 多 Agent 的选择逻辑（见 4.1）
4. **文档路由**——唯一指向 `.spec/INDEX.md`（见 3.3）
5. **全局约束**——安全红线、合规要求、性能基线
6. **维护与校验**——维护职责矩阵、生命周期操作、全局更新校验机制、**任务执行锚点机制规定**、**Git 提交追踪机制规定**、**当前任务锚点**
7. **临时目录约定**——唯一临时目录、判定标准与豁免范围（见 4.6）
8. **展示窗口指引**——说明 `README.md` 的定位与用途，并提供指向 `README.md` 的有效链接
9. **子目录职责边界**——每个顶层目录的一句话职责声明

### 3.5 README.md 特殊定位

> 来源：§4.3.1、§13.5.5

- **定位**：实例层特殊延伸文档，面向人类的展示窗口；纳入规约体系实例层管辖，受全部层级校验规则约束
- **位置**：仓库根目录 `README.md`；按 3.1 的实例层区分规则**不放入** `.spec/`，但须在 `.spec/INDEX.md` 的「实例层文档索引」区块中登记
- **固定结构**（须按顺序包含）：
  1. 项目名 + 一句话项目描述（控制在 30 字以内）
  2. 快速开始（安装/构建、运行、常用命令）
  3. 核心概念（关键术语，每条不超过两行）
  4. 规约体系指引（指向 `AGENTS.md` 与 `.spec/INDEX.md`）
- **元信息区**：YAML front matter 强制包含 `type: instance`、`scope: instance`、`human-facing: true`
- **生命周期**：遵循 4.3 定义的完整五态
- **禁止包含**：规约体系硬性规则全文复制、实例层实现细节、与上层规约相矛盾的陈述、与规约体系无关的推广营销文字
- **校验归属**：修改 `README.md` 时必须触发全局校验（见 4.5、5.4），含展示窗口一致性校验

### 3.6 产物文件清单汇总

> 来源：§3~§5、§13

| 路径 | 体系身份 |
|------|---------|
| `AGENTS.md` | 仓库根目录；体系总入口 + 约束层唯一载体 + 约束层自索引 |
| `.spec/INDEX.md` | `.spec/` 内容唯一索引入口；顶部含体系总入口回链；含知识层/实例层两个索引区块 |
| `.spec/` 下知识层文档 | 知识层载体；可按领域建子目录 |
| `.spec/task-records/` | 锚点机制详情层；每任务一个记录文件；独立于三层体系 |
| `README.md` | 仓库根目录；实例层特殊延伸文档（人类展示窗口）；须经 INDEX 登记 |
| 项目各处实例层实际文档 | 实例层载体；位于业务自然位置；须经 INDEX 登记 |
| 项目自有 `docs/` 等既有文档 | 若判定为知识层：实体留原处不迁移；须经 `.spec/INDEX.md` 知识层索引区块登记 |
| `_temp/` | 唯一临时目录；不属规约体系；须加入 `.gitignore`（见 4.6） |
| `.gitattributes` | 仓库根目录；**条件触发**产物——跨平台协作或 `core.autocrlf=true` 时强制提供，用于固定行尾（见 4.8.6） |

## 4. 规约要求包含的机制

### 4.1 运行模式选择机制

> 来源：§5.1

- `AGENTS.md` 中必须定义**单 Agent / 多 Agent** 的选择逻辑
- 该章节使后续 Agent 能自行判定当前任务应采用何种执行模式，无需依赖外部指令

### 4.2 文档元信息区机制

> 来源：§8.3

**适用范围**：所有知识层与实例层文档（含 `README.md`）强制包含 YAML front matter；`_temp/` 内文件豁免（见 4.7.7）

**必填七字段**

| 字段 | 说明 | 合法取值 |
|------|------|---------|
| `title` | 文档标题 | 自由文本 |
| `type` | 文档类型 | `constraint` / `knowledge` / `instance` / `index` / `config` |
| `scope` | 作用域 | `global` / `domain` / `instance` |
| `status` | 生命周期状态 | `draft` / `active` / `deprecated` / `archived` / `exempt`（见 4.3） |
| `owner` | 责任人 | 由 `{{OPERATOR}}` 变量注入（见 6.4） |
| `last-updated` | 最后更新日期 | `YYYY-MM-DD` |
| `tags` | 标签列表 | 数组 |

**豁免专用字段**（仅在获得层级冲突豁免时添加）

- `exemption.conflicts-with`：冲突的高层级条款
- `exemption.justification`：豁免理由
- `exemption.approved-by`：审核人
- `exemption.record-id`：豁免台账记录路径

### 4.3 文档生命周期机制

> 来源：§8.2

五态定义及各自允许操作：

- **`draft`**——草稿，未审核；允许编辑、提交审核
- **`active`**——生效中；允许编辑（需记录变更）、引用
- **`deprecated`**——已废弃，待归档；只读，不再引用
- **`archived`**——已归档；只读，仅用于历史追溯
- **`exempt`**——豁免（经正式审批）；按豁免条款执行

> 状态流转的操作时序见 5.2。

### 4.4 维护职责机制

> 来源：§8.1

| 操作 | 责任人 | 触发条件 | 校验要求 |
|------|--------|---------|---------|
| 新增知识层文档 | 开发者 / Agent | 新领域知识产生 | 更新 `.spec/INDEX.md` 知识层索引区块，添加元信息区 |
| 新增实例文档 | 开发者 / Agent | 新模块 / 功能上线 | 更新 `.spec/INDEX.md` 实例层索引区块，添加元信息区 |
| 修改约束层 | Tech Lead / 架构师 | 规则变更 | 全局影响评估，通知所有相关方 |
| 废弃文档 | 文档 Owner | 内容过时 | 标记 `status: deprecated`，保留 30 天后归档 |
| 新增 / 修改 `README.md` | 开发者 / Agent | 项目入口需要更新 | 同步更新 `AGENTS.md` 展示窗口指引，触发全局校验 |
| 重构文档结构 | Tech Lead | 结构不合理 | 全量链接检查，更新 `.spec/INDEX.md` |
| 执行 git 提交 | 任务执行 Agent / 主协调者（F 协调员） | 锚点节点触发或人工要求 | 路径限定提交，消息含任务锚点 ID，登记 `关联提交`（见 4.8） |

### 4.5 全局更新校验机制

> 来源：§8.4

每次对规约体系进行修改后，必须执行以下七项校验：

1. **链接完整性**——所有相对路径链接目标存在
2. **元信息完整性**——所有文档包含必填字段（见 4.2）
3. **层级一致性**——无实例层内容出现在知识层，反之亦然
4. **INDEX 同步性**——所有文档在 `.spec/INDEX.md` 对应区块中有条目
5. **约束力合规**——无文档违反约束层规则
6. **展示窗口一致性**——`README.md` 内容不与上层规约矛盾
7. **提交合规性**——锚点与提交双向绑定、提交消息格式、无破坏性命令、无未跟踪交付物（GV-01~GV-05，见 4.8.7）

> 校验的触发时机与执行顺序见 5.4。

### 4.6 临时目录约定机制

> 来源：§0.1、§13.8-3

`AGENTS.md` 必须包含「临时目录约定」章节，其内容须涵盖以下五要素：

- **唯一临时目录**——仓库根目录下的 `_temp/`
- **判定标准**——目录名以下划线开头**且**在构建指令中被显式声明，方可视为临时目录；Agent 不得自行认定其他目录为临时目录或扩大豁免范围
- **豁免范围**——`_temp/` 内文件不纳入三层规约体系、无需 YAML 元信息区、不触发任务锚点机制
- **清理与归档判定标准**
  - 内容已被后续产出物吸收或已过时 → 直接清理
  - 内容含可追溯价值（如校验报告、扫描清单）→ 移入 `.spec/task-records/assets/` 并在对应任务记录中登记链接后，再清空 `_temp/`
- **版本控制要求**——`_temp/` 必须加入 `.gitignore`

**与 `.spec/` 的性质对照（必须严格区分）**

`_temp/` 与 `.spec/` 同为仓库内的特殊目录，但要求**完全相反**：

| 对照项 | `_temp/` | `.spec/` |
|--------|----------|----------|
| 体系身份 | 不属规约体系 | 规约体系正式内容载体 |
| 版本控制 | **必须**加入 `.gitignore` | **严禁**加入 `.gitignore`，必须纳入版控 |
| YAML 元信息区 | 豁免 | 强制 |
| INDEX 登记 | 豁免 | 强制 |
| 全局校验 | 豁免 | 强制接受 |
| 锚点机制 | 操作不触发 | 修改须触发 |

- **判定标准澄清**：本节临时目录判定标准为「目录名以下划线开头**且**在构建指令中被显式声明」；`.spec/` 以点开头且未被声明为临时目录，因此**不属于**临时目录，不享有任何豁免

### 4.7 任务执行锚点机制

#### 4.7.1 三层追踪结构

> 来源：§8.5、§13.2

- **规定层**
  - 载体：`AGENTS.md` 中的机制规定章节
  - 职责：机制说明与规则定义
  - 更新频率：写入后基本不变，仅在显式指令要求时变更
- **锚点层**
  - 载体：`AGENTS.md`「当前任务锚点」章节
  - 职责：最新一次任务的 5 秒摘要（目标、状态、时间、要点、详情索引）
  - 更新频率：每次任务开始时覆写，关键节点时更新状态
- **详情层**
  - 载体：`.spec/task-records/` 目录
  - 职责：每任务一个 md 文件，逐步追加详细执行记录
  - 更新频率：随任务推进实时追加

#### 4.7.2 任务触发判定

> 来源：§8.5.2

满足以下**任一**条件即视为「任务」，纳入锚点机制管控：

1. **涉及实际操作**——对非临时目录中的文件执行了创建、修改、删除、移动中的任何一项
2. **多 Agent 协作**——提示词显式要求，或 Agent 分析后实际使用了多 Agent 工作方式
3. **长任务多步骤**——Agent 决策规划的任务步骤 ≥ 5 步

> 注：临时目录 `_temp/` 中的操作不计入（见 4.7.7）。

#### 4.7.3 锚点层初始结构

> 来源：§13.4

构建时须将以下结构**原样写入** `AGENTS.md`（紧随锚点机制规定之后）：

```text
## 当前任务锚点

- **任务目标**：（尚无任务记录）
- **任务状态**：`无`
- **开始时间**：—
- **最后更新**：—
- **要点摘要**：—
- **详情索引**：—
- **关联提交**：—
```

#### 4.7.4 详情层文件命名

> 来源：§13.5.2

- 命名格式：`<YYYY-MM-DD>-<task-slug>.md`
- 示例：`2026-07-21-build-agent-spec.md`、`2026-07-22-fix-routing-links.md`
- 存放位置：`.spec/task-records/`

#### 4.7.5 详情层文件结构模板

> 来源：§13.5.3

每个任务记录文件须包含以下六段结构：

```markdown
# 任务记录：<任务目标一句话>

## 摘要
- **任务目标**：<与锚点层一致>
- **任务状态**：<与锚点层一致>
- **开始时间**：
- **最后更新**：
- **要点摘要**：<与锚点层一致>
- **操作人**：{{OPERATOR}}

## 用户输入
<完整记录用户提示词（原文或关键段落）>

## Agent 理解与决策

## 执行流程

### 流程概览
- 总步骤数：N
- 多 Agent 协作：是/否（若是，列出子 Agent 数量与分工）

### 步骤记录
#### Step 1: <步骤名>
- 状态：✅ 已完成 / 🔄 执行中 / ⏸️ 中断 / ❌ 失败
- 执行内容：<做了什么>
- 涉及文件：<读取/创建/修改/删除的文件列表>
- 决策记录：<若有分歧点，记录决策及理由>
- 子 Agent（若适用）：<编号、任务、结果>

## 涉及文件汇总
| 操作类型 | 文件路径 | 说明 |
|---------|---------|------|
| 读取    | ...     | ...  |

## 关闭标识
- **完成时间**：
- **最终状态**：✅ 全部完成 / ⚠️ 部分完成 / ❌ 失败
- **关闭说明**：<一句话>
```

#### 4.7.6 详情层写入规则

> 来源：§13.5.4

- **逐步追加**——每完成一个关键节点即追加对应记录，禁止一次性写入全部
- **禁止编造**——只记录实际发生的事情，未执行的不写
- **先有后写**——操作完成 → 记录写入，不可先写记录再执行
- **中断标记**——若在某步骤中断，该步骤状态标记为 ⏸️ 并注明中断原因（若可知）
- **续接标记**——重启继续时，在中断步骤处追加「续接」标记，注明续接时间

#### 4.7.7 临时目录豁免

> 来源：§8.5.2 注、§13.7

- `_temp/` 内的操作**不触发**锚点机制
- `_temp/` 内文件**无需**写入详情层记录
- `_temp/` 内文件**无需** YAML 元信息区

#### 4.7.8 关键约束

> 来源：§13.7

- **锚点极简**——锚点层永远只存「5 秒能读完」的摘要，详情一律外链
- **机制恒定**——规定层一经写入，非显式指令不得修改
- **校验先于信任**——重启时必须「读→比→确认」，绝不直接采信记录
- **实时更新**——关键节点（开始、完成、进入、退出）必须同步更新记录
- **关注当下**——锚点层只存最新任务，只索引最新记录文件
- **禁止编造**——记录内容必须与实际执行对齐
- **临时目录豁免**——`_temp/` 等临时目录中的操作不触发本机制

### 4.8 Git 提交追踪机制

> 来源：新增机制（源提示词 v2.4 无此机制）；配合 4.7 任务执行锚点机制使用，经 2026-09-14 裁决 C-1~C-7 定稿

**设计目的**

- 以任务锚点给 git 提交「打桩」，使**任务语义**与**版本快照**双向对应，形成完整可靠的可追溯日志
- 保证任何异常均可完整回滚溯源，不产生不可逆损害

#### 4.8.1 触发时机

**任务维度**（任务判定依据 4.7.2，四个节点各对应一次提交）

| 节点 | 提交类型 | 强制性 |
|------|---------|--------|
| 任务开始前 | 干净基线提交（不含本次任务改动） | 强制 |
| 关键节点完成时 | 中途检查点提交 | **可选**（由 Agent 判定必要性） |
| 任务结束时 | 成果提交 | 强制 |
| 重启 / 继续时 | 以中断点 WIP 提交为起点，**不重复提交** | 强制 |

**非任务维度**（对应 5.1.4 方案 C）

- 允许提交，但须**同时满足**三条件：① 有实际内容变更 ② 有语义价值 ③ 非中间态产物
- 且须经人工确认，或由人工显式要求

**双向绑定（强制）**——每次提交后，将 commit hash 同时登记至两处：

1. 锚点层「当前任务锚点」的 `关联提交` 字段（可多值，按时间顺序列出本任务全部 hash）
2. 详情层 `.spec/task-records/<任务记录>.md` 的对应节点

**空提交不产生**：工作区无实际变更时跳过该次提交，并在详情层记录「无变更，已跳过」

#### 4.8.2 提交范围与消息格式

- **路径限定**——只提交本次任务涉及的路径；**禁止** `git add -A` 裹挟无关变更
- **在途变更处置**——检测到非本次任务的未提交变更（尤其人工未提交的修改）时，默认**不提交并上报**，由人工裁决；**严禁**代替他人提交其未完成工作
- **消息格式（强制模板）**

  ```text
  <类型>(<任务锚点ID>): <一句话摘要>

  - 关联文件：<路径列表>
  - 验证结果：<校验/测试结论>
  ```

  - 类型取值：`feat` / `fix` / `docs` / `chore` / `refactor` / `test`
  - 非任务态提交以 `chore` 或 `docs` 开头，`<任务锚点ID>` 位置写作 `[非任务]`
- **默认不 push**——提交为本地快照；push 属对外动作，须人工确认后执行

#### 4.8.3 回滚语义

- **允许**：`git revert`，或新建「修复提交」
- **禁止**：`reset --hard`、`rebase -i`、`push --force`、`filter-branch`、`gc --prune`
- 回滚前须在任务记录中登记目标 commit hash 与回滚原因
- **删除前置备份（红线）**——删除**未跟踪**文件（git 无法恢复）前，必须先备份或先纳入版本控制

#### 4.8.4 权限与并发

- **提交权持有者**
  - 单 Agent 场景：当前任务的执行 Agent
  - 多 Agent 场景：收归**主协调者（F 协调员）**
- 其余角色（A 扫描员 / B 分析师 / C 架构师 / D 撰写员 / E 校验员）**只产出文件，不得提交**；E 校验员不持有提交权（校验与提交分离，避免自证）
- 提交前检查 `index.lock` 残留；存在残留即中止提交并上报，**不得**强制删除锁文件

#### 4.8.5 失败与例外

- **任务失败或中断**：允许提交，但**必须**
  1. 在提交消息与锚点状态中标记 `WIP/中断`
  2. 记录已完成边界（哪些步骤已完成、哪些未开始）
- **恢复**：以该 WIP 提交为起点，按 4.7.6 的「续接标记」规则续接，并执行「读→比→确认」
- **临时目录豁免**：`_temp/` 内文件的创建与删除**不触发**本机制（依 4.6、4.7.7）

#### 4.8.6 行尾一致性要求

- **条件触发**——目标项目满足**任一**条件时，必须提供 `.gitattributes` 固定行尾：
  1. 存在跨平台（Windows / Linux / macOS）协作
  2. `core.autocrlf` 为 `true`
- **条款内容**——显式声明文本文件行尾策略（如 `* text=auto eol=lf`），**禁止**依赖 `core.autocrlf` 隐式转换
- **理由**——隐式转换会在 checkout 时将文本文件整体改写行尾，制造「全文改动」的假差异，破坏「提交 = 可审阅快照」这一前提

#### 4.8.7 校验条款

以下检查项纳入 5.4 全局校验流程的「提交合规性」环节：

| 编号 | 检查内容 | 判定方式 |
|------|---------|---------|
| GV-01 | 已关闭任务锚点在锚点层 `关联提交` 字段中至少登记 1 个 commit hash | 字段非空校验 |
| GV-02 | 上述 commit 的消息含该任务锚点 ID | 消息格式匹配 |
| GV-03 | 受控目录（`.spec/` 及实例层登记文档）无未跟踪交付物 | 工作区状态检查 |
| GV-04 | 任务记录中无破坏性命令使用痕迹（见 4.8.3 禁止清单） | 记录内容审查 |
| GV-05 | 工作区无残留 `index.lock` | 文件存在性检查 |

**校验时机**：任务关闭后、非任务态提交后

## 5. 工作流

### 5.1 任务执行流程

> 来源：§13.6

#### 5.1.1 行为定性与策略路由

Agent 接受指令启动后，在完成分析决策、确定要进行实际操作**之前**：

1. 读取 `AGENTS.md` 锚点层，判断是否为新任务
   - 锚点层状态为 `无` 或 `已完成` → 可能是**新任务**
   - 锚点层状态为 `执行中` 或 `已中断` → 可能是**已有任务延续**
2. 若为新任务，按 4.7.2 的任务定义判断本轮行动是否属于任务
   - 是 → 执行**方案 A**
   - 否 → 执行**方案 C**
3. 若为已有任务延续 → 执行**方案 B**

#### 5.1.2 方案 A：新任务

1. 覆写 `AGENTS.md` 锚点层（目标、状态＝执行中、时间、摘要、详情索引）
2. 在 `.spec/task-records/` 创建本任务记录文件，写入摘要 + 用户输入 + Agent 理解
3. 执行**干净基线提交**（不含本次任务改动），并将 commit hash 登记至锚点层 `关联提交` 字段（见 4.8.1）
4. 执行流程部分写入流程概览，各步骤标记为「未执行」
5. 随任务推进，每完成关键节点：更新锚点层状态 + 追加详情层步骤记录；**可选**执行中途检查点提交（见 4.8.1）
6. 全部完成后：锚点层状态改为 `已完成`，详情层写入关闭标识，执行**成果提交**并登记 hash，随后触发提交合规性校验（见 4.8.7）

#### 5.1.3 方案 B：已有任务延续

1. 读取锚点层摘要 + 详情层对应记录文件
2. 执行「**读 → 比 → 确认**」三步校验
   - **读**：读取记录中声称的文件变动
   - **比**：与文件实际状态交叉验证
   - **确认**：确认记录与现实一致后才可继续
3. 确定当前状态并分支处理
   - 执行中 / 未开始 → 在中断节点处标记「续接」，从该节点继续
   - 已完成 → 判断为**复盘**：消除关闭标识，标记「复盘模式」，复盘结束后重新关闭
4. 若上次为**中断**状态：以中断点 WIP 提交为起点续接，不重复执行基线提交（见 4.8.5）
5. 随任务推进，正常更新锚点层和详情层（含 `关联提交` 字段与详情层 hash 登记）
6. 全部完成后：写入新的关闭标识，执行**成果提交**并登记 hash，随后触发提交合规性校验（见 4.8.7）

#### 5.1.4 方案 C：非任务

- 不触发锚点机制，直接执行指令
- **非任务态提交（按需）**：仅当同时满足「有实际内容变更 + 有语义价值 + 非中间态产物」三条件，且经人工确认或人工显式要求时，方可提交（见 4.8.1）；提交消息以 `chore` 或 `docs` 开头并标注 `[非任务]`，提交后触发提交合规性校验（见 4.8.7）

### 5.2 文档维护流程

> 来源：§8.1、§8.2、§8.4（时序抽取）

**新增文档流程**

1. 按层级判定归属（依据 2.4 管辖范围边界）
2. 在正确位置创建文档（**新增**知识层文档 → `.spec/`；实例层实际文档 → 项目业务自然位置；项目**既有** `docs/` 等文档 → 留原处不迁移，仅登记索引）
3. 补全 YAML 元信息区七字段（见 4.2），`status` 置为 `draft` 或 `active`
4. 在 `.spec/INDEX.md` 对应区块登记条目（知识层区块 / 实例层区块）
5. 触发全局校验（见 5.4）

**修改文档流程**

1. 执行内容改动
2. 更新元信息区 `last-updated` 字段
3. 若为 `active` 状态文档，须记录变更
4. 若改动涉及 `README.md`，同步检查 `AGENTS.md` 展示窗口指引
5. 触发全局校验（见 5.4）

**废弃与归档流程**

1. 内容过时 → 将 `status` 改为 `deprecated`，文档转为只读、不再被引用
2. 保留 30 天
3. 期满 → 将 `status` 改为 `archived`，仅用于历史追溯
4. 从 `.spec/INDEX.md` 相应区块移除或标注归档状态
5. 触发全局校验（确认无死链、无孤立引用）

### 5.3 冲突豁免流程

> 来源：新增机制（豁免规则见 2.6）

1. **书面说明**——申请人记录：冲突的高层级条款（精确到章节）、实际业务需求、不存在替代方案的论证
2. **审核确认**——Tech Lead / 架构师审核，确认 2.6 的三项触发条件成立且不属四类禁止情形；结论为通过或驳回
3. **声明豁免**——审核通过后，在低层级文档的 YAML front matter 中添加 `exemption` 字段（`conflicts-with` / `justification` / `approved-by` / `record-id`），并将 `status` 置为 `exempt`
4. **登记台账**——在 `.spec/task-records/` 中创建豁免记录文件，登记豁免编号、时间、冲突条款、业务原因、审核人；`record-id` 指向该文件

### 5.4 全局校验流程

> 来源：§8.4（时序抽取）

**触发时机**

- 任何对规约体系文档的新增、修改、废弃、归档操作完成后
- `README.md` 任何修改后（含展示窗口一致性校验）
- 文档结构重构后（须做全量链接检查）
- 任务关闭后、非任务态提交后（提交合规性校验，见 4.8.7）

**执行顺序**

1. 链接完整性 → 2. 元信息完整性 → 3. 层级一致性 → 4. INDEX 同步性 → 5. 约束力合规 → 6. 展示窗口一致性 → 7. 提交合规性（GV-01~GV-05，见 4.8.7）

**结果处置**

- 全部通过 → 本次变更生效
- 存在不通过项 → 修复后重新执行全量校验；不得跳过或降级校验项

## 6. 其他要求

### 6.1 设计原则

> 来源：§9

以下原则贯穿整个规约体系：

- **单一事实源**——每条规则/知识只在权威位置定义一次，其他地方通过引用获取
- **渐进式披露**——Agent 先读 `AGENTS.md` 获得概览，按需深入，不被信息淹没
- **机器可读优先**——结构化元数据 > 自然语言描述；链接 > 文字指引
- **显式优于隐式**——所有假设、约定、例外都必须书面化
- **关注当下**——锚点层只记录最新任务，历史详情通过外链追溯

### 6.2 链接规范

> 来源：§5.3

- 所有跨文档引用必须使用**相对路径**
- 链接文本必须具有**描述性**（禁止「点击这里」）
- 每个 INDEX 文件必须是**纯导航文件**，不包含实质内容

### 6.3 防重复与单一真相源要求

> 来源：新增（承 6.1 单一事实源原则）

- **禁止**在 `.spec/INDEX.md` 中复制、罗列或摘要 `AGENTS.md` 的章节清单与规则内容
- 约束层章节的**唯一真相源**是 `AGENTS.md` 自身，以防索引与正文漂移
- `.spec/INDEX.md` 顶部的体系总入口回链**仅为指针**，不携带任何约束层内容
- `README.md` **禁止**复制规约体系硬性规则全文（见 3.5）

### 6.4 操作人变量注入要求

> 来源：§0

- 规约体系中所有需要标注**责任人、开发者、作者、owner、操作人**的位置，统一使用 `{{OPERATOR}}` 变量值填充
- 若构建指令未显式传入该变量，则默认填充为 `用户`
- Agent **不得**自行编造该字段，也**不得**留空
- 影响位置：全部产物文档元信息区的 `owner` 字段（见 4.2）、任务记录文件的「操作人」字段（见 4.7.5）

### 6.5 隐藏目录可发现性要求

> 来源：新增（承 6.1 显式优于隐式原则）

**风险说明**

- `.spec/` 为隐藏目录（点前缀），默认可能被以下场景忽略：文件树不显示、`**/*.md` 类 glob 模式跳过 dotdirs、部分代码搜索工具默认排除隐藏路径
- 若 Agent 扫描时未覆盖 `.spec/`，可能误判「规约体系不存在」并重复构建，或直接跳过约束层规则

**硬性要求**

- **要求 1（工具行为）**：Agent 使用 glob、代码搜索、目录遍历等工具扫描仓库时，**必须显式包含 dotfiles 与 dotdirs**，不得依赖工具默认行为；扫描结果须能覆盖 `.spec/` 全部内容
- **要求 2（入口可见性）**：体系入口链路必须全部位于**非隐藏**位置或显式声明，具体由以下三处共同保证，不在此重复定义：
  - `AGENTS.md`（非隐藏，仓库根目录）的「文档路由」章节显式指向 `.spec/INDEX.md`（见 3.3、3.4 第 4 项）
  - `README.md` 的「规约体系指引」显式指向 `AGENTS.md` 与 `.spec/INDEX.md`（见 3.5）
  - `.spec/INDEX.md` 顶部保留指向 `AGENTS.md` 的向上回链（见 3.3 ③）
- **要求 3（构建期自检）**：构建完成后须验证——从一个干净克隆出发，仅按 `AGENTS.md` → `.spec/INDEX.md` 路径可完整抵达全部知识层与实例层索引条目，无需依赖目录列举
