# strategy.md — 简历编写与投递策略

> **定位**：本文件负责**实例构建（阶段 A）**与**投递快照（阶段 B）**两个可选操作，是其实例定制操作流程与实例构建方案的唯一权威文档；**PDF 构建**为第三个平级可选操作，见 `build-pdf.md`。
> **分工**：母版维护走 `AGENTS.md` §4.1；实例登记见 [`INDEX.md`](INDEX.md) §2；投递 tag 规范见 [`tag.md`](tag.md)，日志见 [`TargetCompanies.md`](TargetCompanies.md)。

## 定制投递流程（三项操作平级、各自独立、均须显式要求）

> **实例构建**、**投递快照**、**PDF 构建**是三个平级、彼此独立的可选操作，各自仅在提示词显式要求时执行；体系内不存在"做了 A 就必须做 B"的关联包含关系。实例构建产出可投的实例版本；投递快照基于任一已构建的 `active` 实例执行——可重复、构建后不投也合法、投递无需重新构建。PDF 构建为独立操作，见 `build-pdf.md`。

### 阶段 A：实例构建（产出一个可投版本）

1. **选取目标**：从 [`TargetCompanies.md`](TargetCompanies.md) 按公司性质分组选取目标公司。目标公司**必须能在该文件查到**——公司名逐字一致，或去除括号内容/别名后一致；**查不到即停止并报告**，禁止外部推断或"按主营业务模糊匹配"。
2. **复制模板并命名**：复制 `Resume-Lite.md`，重命名为 `Resume-{目标}-{版本}-base.md`（如 `Resume-金融科技-v1.0-base.md`）——**构建时就确定版本号并命名好**，`-base` 尾缀标识这是实例本体。禁止直接改动模板。补充规则：
    - 命令：`cp Resume-Lite.md Resume-{目标}-{版本}-base.md`（在仓库根目录执行）。
    - `{目标}` 由用户提示词指定（**分组名或公司名均可**），须与后续所用构建方案对应；实例 md 落盘于**仓库根目录**（与母版/Lite 同层，非 `docs/`）。
    - 版本号：**首个实例独立起算 `v1.0`**（不关联母版基线 tag 版本）；内容实质修改升次版本（`v1.0` → `v1.1`），仅错字润色沿用当前版本。
    - 本复制重命名属实例构建/投递常规动作，免 LOG 登记，由 INDEX §2 台账 + commit 追溯。
3. **填充内容**：基于母版 `Resume.md` 的内容填充实例：**将所选方案的示范条目（3–4 个，按清单顺序）插入「重要经历」章节下**；求职意向、相关知识技能等既有章节按下方补充规则处理（实例内容偏离母版属定制的意义，结构基准源自模板）。补充规则：
    - 选择键统一为「适用领域分组」——同分组内的岗位差异，由方案内要点字段的分支选择承担；TargetCompanies「关注岗位」为空时以分组为准。
    - 实例「求职意向」（Lite 模板占位）**沿用母版求职意向原文**（`Resume.md`「求职意向」），除非方案或用户提示词另行指定。
    - **母版为事实源（里子），方案示范为定稿呈现（面板）**，Agent 仅做复制拼接与受控适配——对应分组的方案空缺时，**停止并报告，禁止回退母版自由手裁**。
4. **登记实例**：立即在 [`INDEX.md`](INDEX.md) §2 台账登记（只记 md 源文件，PDF 产物不入账，状态 `active`），提交 `docs(resume): 登记 {目标指向} v{版本} 实例`（"目标指向"即实例文件名中的 `{目标}` 值）。

> PDF 构建不属本阶段，为独立可选操作（见 build-pdf.md）。

### 实例校验

校验**实例 md**：①所选方案条目 3–4 个且按清单顺序完整落入「重要经历」②无占位符残留、求职意向已按规则替换 ③去空白码点 ≤2200（口径见字数预算表注）。**页数校验属 PDF 构建操作**（见 `build-pdf.md`）。
（此为实现"保留以 PDF 页数保证 ≤2 页的方法"：设计期用字数预算前置保证，构建期用闸门 + 页数校验，二者互指。）

### 阶段 B：投递快照（基于已有实例的一次投递）

前提：存在任一 `active` 状态的实例（刚构建的，或历史构建的——**无需重新构建**）。

1. **选取实例版本**：从 `INDEX.md` §2 的 `active` 实例中选定本次投递所用的文件；如需内容调整，先回阶段 A 迭代出新版本（新版本 = 新的 `-{版本}-base` 文件）。
2. **生成投递副本**：将所选 `Resume-{目标}-{版本}-base.md` 复制一份，尾缀 `-base` 改为 `-{投递公司名称}-{YYYYMMDD}`，得到 `Resume-{目标}-{版本}-{投递公司名称}-{YYYYMMDD}[-{N}].md`（如 `Resume-金融科技-v1.0-招银网络-20260910.md`）——**文件名即投递记录**，实际投出的就是这份副本。本复制重命名属实例构建/投递常规动作，免 LOG 登记，同日同公司多次投递时，在日期后追加 `-{N}` 序号（与 tag 的 `-N` 规则一致，见 [`tag.md`](tag.md)）。由 INDEX §2 台账 + commit 追溯。（示例公司名「招银网络」为简称；公司名写法以 `TargetCompanies.md` 该行**规范名**为准——如该行为 `招商系（招商证券/招银网络科技）`；日期统一 `YYYYMMDD`。）
3. **打投递快照 tag**：`git tag v{版本}-{投递公司名称}-{YYYYMMDD}`——与投递副本文件名的版本 / 公司 / 日期三要素一致；格式与铁律见 [`tag.md`](tag.md)。
4. **记录投递日志**：在 [`TargetCompanies.md`](TargetCompanies.md) 的投递日志追加一行（日期 / 简历文件 / 目标公司 / 对应 tag），其中「简历文件」填**投递副本文件名**、「对应 tag」填本次快照 tag（同日同公司多次投递的 `-N` 后缀规则见 [`tag.md`](tag.md)）；不覆盖旧记录。
5. **更新状态**：公司清单中该公司的「投递简历 / 状态」列更新为最新进展（`投递中` / `一面` / `二面` / `offer` / `挂`），「投递简历」填投递副本文件名；`INDEX.md` §2 该实例的「对应 tag」列更新为**最新一次**投递的 tag。
6. **提交落盘**：按 AGENTS.md §5.2 默认提交改动（**`docs(resume)` 类型**，subject 含公司名、日期与投递目标，如 `docs(resume): 投递 金融科技 v1.0 → 招银网络 20260910`）；提交失败须明确上报。本次提交统一覆盖投递副本、INDEX §2 与 TargetCompanies 状态等全部关联改动——**均为 md 与台账改动，不含 PDF 产物**（PDF 构建为独立可选操作，见 [`build-pdf.md`](build-pdf.md)）。（subject 中含公司名时，须与投递副本文件名、投递日志一致。）

> 投递动作（线下发送）不在本流程内——阶段 B 产出「投递副本 md + tag + 投递日志 + 状态更新」即完成；**投递副本 PDF 非必需**，仅在提示词显式要求 PDF 构建时另行产出（见 [`build-pdf.md`](build-pdf.md)）。

## 实例构建方案设计

> **方案库定位**：为不同目标类型提供**确定性生成规格**——构建实例（阶段 A 第 3 步）时，按目标公司所属分组匹配对应方案执行。  
> 方案按 [`TargetCompanies.md`](TargetCompanies.md) 的公司性质分组组织；项目的取舍依据是 [`INDEX.md`](INDEX.md) §1「相关领域」。  
> 各分组的**客户群体与判定边界**见 [`TargetCompanies.md`](TargetCompanies.md) 的「分组定义」节。  
> **确定性验收标准**：条件不变（母版、模板、目标公司、LLM 模型、Agent 软件、操作模式均不变）时，依据方案生成实例，**无论执行多少次，产出结果都相同**——方案内禁止"酌情 / 参考 / 适当 / 视情况"类模糊表述。  
> **PDF 约束**：任何实例生成的 PDF 不超过 2 页（上限 **2200**，由字数预算前置保证——属设计期约束；构建侧的字数闸门与页数兜底机制见 `build-pdf.md`）。上限由 2026-09-11 标定实验锁定（实测 2239 仍为 2 页 / 2280 已为 3 页），见下方字数预算。
> **结构说明**：方案库（原 10 组单节）已拆分为 `docs/strategy/` 下 10 个独立文件，本文件仅保留通用规则 + 模板 + 索引；运行时按索引按需加载对应分组文件，禁止一次性全量读取。

### 方案选择指引（阶段 A 第 3 步的执行流程）

**输入**：目标公司信息（取自 [`TargetCompanies.md`](TargetCompanies.md) 该公司行）+ 用户提示词要求 + 第 2 步复制出的实例副本（`Resume-{目标}-{版本}-base.md`）。

1. **选定方案**：依据目标公司所属的「适用领域分组」匹配方案（一分组一方案，选择键唯一）。`{目标}` 键由用户提示词决定（分组名或公司名均可），但构建方案的选择始终依据目标所属的「适用领域分组」。
2. **选定示范分支**：**当前每个关键项目下仅 1 个示范块，不存在"多示范可选"**。要点含「分支：」后缀时，该子句为**受控适配的差异化指令**（规定该示范在何种目标公司下如何侧重），**不是"选哪个示范"的选择键**；判定输入仅限 [`TargetCompanies.md`](TargetCompanies.md) 该公司行已填写的「关注岗位 / 主营业务 / 其他备注」字段，做字面匹配。字段为空或未命中任何分支关键词时，按示范原文采用（即默认分支）；**禁止依据外部信息或主观推断补出岗位画像**。
3. **内容构建**：将选中示范复制拼接进实例副本。
4. **自适应调整（受控适配）**：允许动作**仅限三类且来源确定**——① 命中的要点含「分支：」指令时，按其原文调整该项目的 bullets 取舍与顺序（指令指明调哪条即只调该条）；② 示范文本中出现目标指向表述（具体公司名或行业泛称）时，替换为本次 `{目标}` 值；③ 要点不含「分支：」时**零调整**、按示范原文采用。**禁止**新增或改写事实、数字、技术名词与章节标题——母版为唯一事实源。

**输出**：符合要求的简历实例（登记见阶段 A 第 4 步）。

确定性边界：自适应调整的规则由要点字段封闭——同一目标公司、同一要点下，调整对象、范围、依据均不变（**要点不含「分支：」即零调整**），结果可复现；要点之外的自由发挥视为违规。

### 方案条目结构约定

每个方案（一个小节）含 3 个字段——方案只展示关键要点与定稿示范，简历只是面板，关键还是里子（由黄泊凯人工把关）：

| 字段 | 含义 |
|---|---|
| 适用领域分组 | 对应 TargetCompanies 的公司性质分组，是方案的选择键。**取值必须与该文件分组名逐字一致**，不得改写、缩写或附加括号注解 |
| 方案构建意图简述 | **方案级验收摘要**——用通俗语言说明本方案预期如何构建实例、如何契合该领域要求并在面试中形成竞争优势。**只存在于方案文件：不进入实例、不占字数预算**；位置在「适用领域分组」之后、「关键优势项目」之前 |
| 关键优势项目 | 有序入选清单（清单顺序即实例中的排列顺序），每项含"要点 + 示范内容" |

**要点字段的三重职责**（构成"示范选择与调整指令"，不构成"内容创作指令"）：

1. **选取理由说明**——为何该项目入选该分组方案；
2. **分支选择指令**——各示范的适用情形，Agent 依据目标公司具体情况选择对应示范；
3. **构建调整参照**——内容构建时对照要点将拼接内容与目标公司对齐（受控适配：动作仅限按「分支：」指令调整对应 bullets、替换目标指向，见「方案选择指引」第 4 步）。

**示范粒度**：单个项目的完整简历条目（从项目标题到要点 bullets 的整段 markdown）。**当前每方案每个关键项目N下恰 1 个示范块，不存在"多示范可选"**；同领域不同类型公司的差异，由要点「分支：」指令承担。**默认分支**：要点不含「分支：」后缀者即默认（通常为关键项目1）；目标公司相关字段为空或未命中任何分支关键词时，一律按示范原文采用，禁止引入 TargetCompanies 未记录的岗位假设。

**字数预算（硬性上限）**：

| 项目 | 预算 |
|---|---|
| 实例全文（**自动构建 / PDF 链路**上限，标定锁定值） | ≤ **2200** 字符 |
| 实例全文（**人工编辑 Word 链路**参考上限，2026-09-24 起） | ≤ **2700** 字符 |
| Lite 模板固有结构（标题/基本信息/教育/技能/重要经历头，去空白实测） | **648** 字符（2026-09-13 标定）⚠️ **2026-09-24 复测为 716；且 Lite 已不再作为构建载体（改人工编辑 Word）→ 该值仅作历史参考，构建期以「实例固定骨架实测表」与构建前闸门为准** |
| 计入预算的单项目示范条目 | 200–**380** 字符 |
| 入选关键优势项目数 | **推荐默认 3–4 个**（完整项目）；**如实际需要可调整**，并可用「**简述型补充条目**」另行补强（不计入该数） |
| 竞赛佐证短列表（不计入单条，计入全文） | 候选池 = `INDEX.md` §1 全 **8 项**赛事；按本域余量精选 **3–5 条**（≈60–200 字符）；**只做选取与排序，不新增赛事** |

> **计数口径**：去空白字符数 = 去掉全部空白字符后的**字符（码点）数**，canonical 实现为 `len(''.join(text.split()))`。**不得使用 `tr -d '[:space:]' | wc -m`**——本机 `wc -m` 按**字节**计（中文 1 字 = 3），会得到约 1.85 倍偏大的数值。计数**含 markdown 标记**（`#`、`**` 等，占比极小），与闸门保持一致，禁止另行剥离。
>
> **两处阈值各自的计数口径（2026-09-21 明确）**：
> - **单项目示范条目 200–380** —— 计数**不含** `` `#### {项目标题} | {角色} | {时间}` `` **标题行**，只计 `**项目概述**` / `**核心工作**` bullets / `**成果**` 等正文（设计期分档口径，记为**口径 A**）。
> - **实例全文 ≤2200 / ≤2700**（双轨，见下）—— 计数**含**标题行在内的**全部** markdown（真实约束口径，记为**口径 B**）；与「2239 仍为 2 页 / 2280 已为 3 页」的**页数标定实验**同口径，也与构建前**字数闸门**（`build-pdf.sh` 对整份 md 执行 `len(''.join(text.split()))`）**完全一致**。
> - **换算参考**：每条标题行约 **25–45 码点**，故 `648 + n×380 + 佐证` 分档算式（口径 A）会**系统性低估**真实全文（口径 B）约 `n × 35`；该算式仅作**档位粗估**，**唯一硬约束以构建前闸门（口径 B ≤ 链路上限，见下双轨）为准**。

**⚠️ 字数上限双轨制（2026-09-24 人工裁决 D-1）**：

- **自动构建 / PDF 链路：≤ 2200** —— 由页数标定实验（**2239 仍 2 页 / 2280 已 3 页**）锁定，**该值不变**；`build-pdf.sh` 闸门与 `pdf-check.py --max-pages 3` 依此链路取值。
- **人工编辑 Word 链路：≤ 2700** —— 自 2026-09-24 起实例改由**人工编辑 Word** 构建，实测 Word 2 页容量大于 PDF 链路，故放宽至 **2700**（覆盖增补后最大组 **2684**，余量 16）。
- **两条链路的阈值互不替代**：人工链路按 Word 实测页数把关；自动链路仍按 2200 与页数兜底把关。

依据：母版单项目条目 716–1559 字符、全文 **9127** 字符（去空白口径，2026-09-11 复测）。**页数标定**：PDF 链路去空白 **2239 仍为 2 页、2280 已为 3 页** → 取 **2200**；**人工 Word 链路上限取 2700**（2026-09-24 人工裁决）。分档结构算式（Lite 固有 **648**、单条上限 380、佐证 60–200）：
- **5 完整项目 + 佐证档**（政企信科，1 组）= 648 + 5×380 + 200 = **2748** ← 理论上限略超 2700，须靠人工把关 / 闸门收口（实际 **2684**，见下）
- **4 完整项目 + 佐证档**（agent / 物联网 / 互联网 / 企业软云 / 垂直领域，5 组）= 648 + 4×380 + 200 = **2368**
- **3 完整项目 + 佐证档**（机器视觉 / 金融证券，2 组）= 648 + 3×380 + 200 = **1988**
- 无佐证档（理论备用）= 上式减去佐证
- **简述型补充条目**（如方案 01 的「智慧物流系统」）：**不设成果行**，**不计入**「完整项目」档位算式；仍受「单项目示范条目 200–380」与「实例全文字数上限」约束

现有 10 组**实测实例体量**（**2026-09-24 复测 · 8 域增补后**）：**8 个启用组** —— **口径 A（不含标题行）1892–2418**，**口径 B（含标题行）2047–2684**；**2 个暂不投递组**（具身智能 / 软件外包，未参增补）仍为 口径 A 1619–1644 / 口径 B 1766–1799。**最大组 `08-政企信科` 2684 ≤ 2700（余量 16）** ✅ —— **增补后已无超限组**；2026-09-23 依 2200 上限标记的 `01-agent 2290` / `08-政企信科 2250` / `04-物联网 2151` 三处，**随上限放宽至 2700 而全部解除**。各方案**文档头「体量状态」行**仍就地标注实测值。

**实例固定骨架（必含，缺一即视为构建缺陷）**：

### 示范块写作强制规范（2026-09-29 · 问题 4/5/6/7 专项）

以下规则为所有方案文件示范块的**强制约束**，构建实例时每个示范块必须满足：

1. **项目背景 + 项目定位双段式**（问题 4）：每个示范块在标题行下必须包含 `**项目背景**` 和 `**项目定位**` 两行，项目背景以"针对 / 面向 / 由于……痛点/瓶颈"开头，不得出现无痛点的项目概述。

2. **相关技术栈一行**（问题 5）：每个示范块的标题行紧接一行 `**相关技术栈**`，用 `/` 分隔关键技术名词。

3. **核心工作 bullet 铁三角**（问题 6）：每条 bullet 必须按「针对[问题/瓶颈] → [方案行动] → [量化结果/工程价值]」三段结构编写。触发词：针对/面临/鉴于 | 方案词：设计/实现/构建/优化 | 结果词：降至/提升至/压缩至/[数字]。禁止纯动作描述。

4. **bullet 数量均匀度**（问题 7）：
   - 实习/项目类完整条目：3-4 条
   - 纵向科研/个人实践：3 条
   - 同份简历内各项目 bullet 数量互差 ≤ 1
   - 单条 bullet 长度上限 160 字
